# Commit Message Format

Every commit message must follow this format:

If the best approach is unclear or you are unsure, ask Emily before proceeding.

```
<type>(<scope>): Concise summary (≤72 chars)

WHY:
- Rationale for the change (what problem this solves)

EXPECTED:
- Observable outcome (test names, behaviors now satisfied)
```

## Types

`feat` | `fix` | `refactor` | `test` | `docs` | `chore` | `perf` | `build` | `ci` | `security`

## Rules

- Imperative mood: "Add" not "Added"
- No tool attribution ("Generated by Augment", etc.)
- WHY explains rationale — the diff shows WHAT, the message explains WHY
- EXPECTED names specific tests or verifiable behaviors
- Commit in GREEN state — before refactoring

## Breaking Changes

Add `BREAKING CHANGE: <description>` in the footer when a public API changes.
